# content-agent review

## Summary (5 lines max)
Seed #1 is confirmed and worse than reported: the literal `SANITY_API_TOKEN` is in `dist/server/chunks/chat_CyN76Ejq.mjs` and also in `dist/server/.dev.vars`. Rotate the token. `dist/client` is clean.
The agent works on the happy path but falls over on edge cases. Sanity errors and null fields give a non-JSON 500, retrieval ignores the visitor's words ("react bookmarks" returns the first 8 alphabetically), prefix regexes misroute intents ("ready" → articles), the reply text's count disagrees with the cards, and there are no request limits.
The grounding check (`compose.ts`) is weaker than its comments claim. It matches substrings, lets numbers through, the ALLOWED list holds praise adjectives, and the facts themselves contain made-up wording ("worked with him at").
The schema, types and queries have drifted: `topics.backgroundColor` is a `string` in the schema but a `color` object in the data, non-required fields are typed non-null, 10 projections are duplicated between `queries.ts` and `retrieve.ts`, and `startDate` is a free-text string that is sorted as text.
Proposal: `packages/sanity` with `./schema` (Studio) and `.` (runtime `createSanity`), named `defineQuery` queries, types generated by `sanity typegen`, a standalone Studio published with `sanity deploy`, and a 12-item fix list for the agent.

## Proposal

### `packages/sanity` (ADR 0007)
```
packages/sanity/
  package.json         exports:
                         "."          → src/index.ts        runtime: createSanity, imageUrl, API_VERSION. Depends only on @sanity/client + groq
                         "./queries"  → src/queries/index.ts named defineQuery exports, no client
                         "./types"    → src/sanity.types.ts  GENERATED by typegen, committed
                         "./schema"   → src/schema/index.ts  schemaTypes (JS/JSX as-is, incl. hero.jsx). Studio only: pulls in `sanity` + React
  schema.json          GENERATED (sanity schema extract), committed
  sanity-typegen.json  { "path": "./src/queries/**/*.ts", "schema": "./schema.json",
                         "generates": "./src/sanity.types.ts", "overloadClientMethods": true }
```
- **Queries.** One file per content type, for example `src/queries/projects.ts` with `projectsQuery` (the browse view) and `projectsForChatQuery` (`[0...$limit]`, `$q` match). Use `defineQuery` from `groq`, and delete the hand-rolled `groq` tag in `queries.ts:22`, because typegen only recognises `defineQuery` or the real `groq` tag. Shared fragments like `IMAGE` stay as `const` template interpolations, which typegen can resolve inside the same module. Add the `countsQuery` and `settingsQuery` files. `src/queries/index.ts` re-exports everything as a `queries` record for `sanity:check`.
- **Factory.**
  ```ts
  export interface SanityConfig {
    projectId: string; dataset: string;
    apiVersion?: string;            // default API_VERSION = "2024-03-09"
    token?: string;                 // Viewer robot token; server only
    useCdn?: boolean;               // default true (works with a token — verified)
    perspective?: "published" | "drafts";   // default "published"
  }
  export function createSanity(config: SanityConfig): {
    client: SanityClient;
    // typed by typegen's SanityQueries overload: result type comes from the query string
    fetch: SanityClient["fetch"];
    imageUrl: typeof imageUrl;
  };
  ```
  It holds no env reading and no module-level state. The caller owns config, which is what keeps it Worker-safe and script-safe.
- **Types.** The generated `sanity.types.ts` replaces `apps/web/src/lib/sanity/types.ts`. Components use `ProjectsQueryResult[number]`. Hand-written UI types (`CardLayout`) move to `packages/ui`.
- **`apps/web` wiring.** `src/lib/sanity.ts`:
  ```ts
  import { createSanity } from "@badger3000/sanity";
  import { PUBLIC_SANITY_PROJECT_ID, PUBLIC_SANITY_DATASET } from "astro:env/client";
  import { SANITY_API_TOKEN, SANITY_PREVIEW } from "astro:env/server";   // secret → runtime getSecret on the Worker
  let s: ReturnType<typeof createSanity> | undefined;
  export const sanity = () => (s ??= createSanity({ projectId: PUBLIC_SANITY_PROJECT_ID!, dataset: PUBLIC_SANITY_DATASET!,
    token: SANITY_API_TOKEN, perspective: SANITY_PREVIEW === "drafts" ? "drafts" : "published",
    useCdn: SANITY_PREVIEW !== "drafts" }));
  ```
  Create it lazily so `astro:env/server` is read per isolate at runtime and never at bundle time. `scripts/sanity-check.ts` calls `createSanity({...process.env})` directly; it can't import `astro:env`. The agent (`retrieve.ts`, later `packages/agent`) receives the instance as an argument and never imports env itself.
- **`apps/legacy-next`.** Don't consume the runtime package. It keeps `lib/sanity.ts` + `types/sanity.ts` until the cutover deletes it, so migration churn on a stack that's going away stays at zero. Its only link is the embedded `/studio` route, which imports `./schema` until `apps/studio` ships. After that, delete `app/studio` and add a redirect.
- **Typegen: what it takes.** The JS/JSX schemas are not a blocker: `sanity schema extract` loads `sanity.config.ts` through the CLI's own bundler, so `hero.jsx` and the plain-object schemas work unchanged. Steps:
  1. `apps/studio`: `sanity schema extract --enforce-required-fields --path ../../packages/sanity/schema.json`. With `--enforce-required-fields`, `Rule.required()` fields become non-optional and everything else becomes `| null`, which fixes #17 by construction.
  2. `packages/sanity`: `sanity typegen generate`, which needs the `sanity` CLI as a devDependency of the package.
  3. Turbo tasks `schema:extract` → `typegen` → `^build`. Commit both generated files so `apps/web` CI doesn't need Studio deps.

  Prerequisites: fix Topics `color` (#14), hoist the inline `retrieve.ts` queries (#16), and switch to `defineQuery`. Estimate: **M** (half a day), mostly hoisting queries and swapping imports in about 17 consumers. **Recommendation: adopt it.**

### Studio as `apps/studio`
- **Move:** `sanity.config.ts` and `sanity.cli.ts` go to `apps/studio/`. `schemas/structure/bookmarkStructure.ts` goes to `apps/studio/structure/` (it is Studio-only). Schemas go to `packages/sanity/src/schema/` and are imported via `@badger3000/sanity/schema`.
- **Deps:** `sanity`, `@sanity/vision`, `react`, `react-dom`, `styled-components`, plus the new `@sanity/color-input` (#14).
- **Config changes:**
  - Drop `basePath: "/studio"`.
  - Env: a standalone `sanity build` only exposes `SANITY_STUDIO_*`, so the `PUBLIC_*`/`NEXT_PUBLIC_*` fallbacks in `sanity.config.ts:7-14` would be undefined in the browser and the config throws. Use the non-secret constants exported from `packages/sanity` instead.
  - `sanity.cli.ts`: add `studioHost: "badger3000"` and `deployment: { autoUpdates: true }`.
- **Hosting.** Recommend **`sanity deploy`** (`badger3000.sanity.studio`): free, Sanity login built in, CORS origin added automatically, auto-updates, no infrastructure. Cloudflare (`sanity build` → static assets at `studio.badger3000.com`) gives you your own domain and lets you put Cloudflare Access in front. The cost: you add the CORS origin with credentials by hand, rebuild for every Studio upgrade, and own one more deploy. Either way, add a `/studio → https://badger3000.sanity.studio` 301 at the cutover.

## Cross-lane notes
- Seed #5: chat cards link to `/articles/${slug}` and `/codepen/${slug}` (`retrieve.ts:172,189`), and both routes are missing. Whoever adds them should reuse `articlesQuery`/`experimentsQuery` plus a `*[slug.current == $slug][0]` detail query in `packages/sanity`.
- Seed #2 (double `init()` in `lib/chat.ts`) doubles `/api/chat` POSTs, which doubles the Sanity calls and the rate-limit budget used per question.
- `lib/chat.ts` needs to render the new `503 {degraded:true}` and `429` replies (agent fixes #2 and #6).
- `site` is apex while `.env.example` `PUBLIC_SITE_URL` is also apex and unused (#13). The apex vs www decision belongs to the platform lane.
- PRD platform: there is no Sanity publish webhook → Cloudflare build hook yet, so browse pages go stale until a manual deploy, while chat reads live data. The two can disagree.
